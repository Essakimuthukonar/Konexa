============================================================
2. CONTAINERIZATION
===================

Containerization is the process of packaging an application together
with its runtime, dependencies, libraries and configuration into a
portable container.

Instead of installing Node.js and application dependencies directly
on the EC2 server, the Konexa application runs inside a Docker
container.

Benefits:

1. Consistent application environment
2. Easy deployment
3. Portability
4. Faster application startup
5. Dependency isolation
6. Easier scaling
7. Simplified CI/CD
8. Easy rollback using image tags

============================================================
3. VIRTUALIZATION VS CONTAINERIZATION
=====================================

Virtualization:

Hardware
|
Hypervisor
|
-

## | VM | VM | VM |

Each VM contains:

* Operating System
* Libraries
* Application

Containerization:

Hardware
|
Operating System
|
Docker Engine
|
-

## | Container | Container |

Each container contains:

* Application
* Dependencies
* Runtime

Virtual machines require a complete guest operating system.

Containers share the host operating system kernel and are therefore
lighter and faster.

7. DOCKERFILE
=============

The Konexa application uses Node.js 22 Alpine as the base image.

Dockerfile:

FROM node:22-alpine

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build

EXPOSE 3000

CMD ["npm", "start"]

Dockerfile instructions:

FROM
Specifies the base image.

WORKDIR
Sets the working directory inside the container.

COPY
Copies application files into the container.

RUN npm ci
Installs the required Node.js dependencies.

RUN npm run build
Creates the production build of the Next.js application.

EXPOSE 3000
Documents the application port.

CMD
Starts the Next.js production server.

16. JENKINS DEPLOYMENT PROCESS
==============================

Stage 1 – Clone Source Code

Jenkins clones:

Branch:
konexa-v3-docker

Stage 2 – Docker Build

Jenkins builds:

muthukonar/konexa:<BUILD_NUMBER>

and:

muthukonar/konexa:latest

Stage 3 – Image Validation

Jenkins verifies the Docker image using:

docker images

docker inspect

Stage 4 – Docker Hub Login

Jenkins authenticates using the configured Docker Hub credential.

Stage 5 – Push Image

Jenkins pushes:

muthukonar/konexa:<BUILD_NUMBER>

muthukonar/konexa:latest

Stage 6 – Prepare EC2

Jenkins connects to:

ubuntu@10.0.1.143

and verifies:

* Docker installation
* Docker service
* Docker access
* Port 3000

Stage 7 – Deploy

The EC2 server pulls:

muthukonar/konexa:latest

The old container is removed:

docker rm -f konexa-v3

A new container is started:

docker run -d 
--name konexa-v3 
-p 3000:3000 
--restart unless-stopped 
muthukonar/konexa:latest

Stage 8 – Verification

Jenkins verifies:

docker ps

docker port konexa-v3

curl http://localhost:3000

Stage 9 – Cleanup

Unused dangling Docker images are cleaned using:

docker image prune -f

17. DOCKER IMAGE VERSIONING
===========================

Each Jenkins build receives a unique build number.

For example:

Build 38:

muthukonar/konexa:38

and:

muthukonar/konexa:latest

This provides two advantages:

1. latest can be used for normal deployment.
2. Versioned tags can be used for rollback.

Rollback example:

docker pull muthukonar/konexa:37

docker rm -f konexa-v3

docker run -d 
--name konexa-v3 
-p 3000:3000 
--restart unless-stopped 
muthukonar/konexa:37

18. TROUBLESHOOTING PERFORMED
=============================

Problem 1:
Docker command was not found in Jenkins.

Error:

docker: not found

Solution:

Docker was installed on the Jenkins agent and the Jenkins user
was given Docker permissions.

---

Problem 2:
SSH Agent plugin error.

Error:

No such DSL method 'sshagent'

Solution:

The Jenkins SSH Agent plugin was installed/enabled.

---

Problem 3:
SSH credential was missing.

Error:

Could not find specified credentials:
konexa-ec2-ssh

Solution:

The existing Jenkins SSH credential:

frontend-agent-ssh

was used.

---

Problem 4:
Docker image deployment failed.

Error:

invalid reference format

Cause:

The Docker image variable was not correctly available inside the
remote SSH heredoc.

Solution:

The remote deployment script explicitly defines:

DOCKER_IMAGE="muthukonar/konexa"

---

Problem 5:
Docker Compose container name conflict.

Error:

Conflict. The container name "/konexa-v3" is already in use.

Cause:

The existing konexa-v3 container was already present.

Solution:

The old container was removed before starting the new deployment.

---

Problem 6:
Docker container remained in Created state.

Error:

failed to bind host port 0.0.0.0:3000:
address already in use

Cause:

The previous PM2-managed Next.js application was already using
port 3000.

Solution:

The old PM2 Konexa applications were removed and Docker was allowed
to take ownership of port 3000.

21. SECURITY CONSIDERATIONS
===========================

The following security improvements are recommended for production:

1. Do not hardcode database passwords.
2. Store secrets in AWS Secrets Manager or Parameter Store.
3. Use Docker secrets or secure environment variables.
4. Use HTTPS with an SSL/TLS certificate.
5. Restrict EC2 security group access.
6. Allow port 3000 only when required.
7. Use SSH keys instead of passwords.
8. Use Docker Hub access tokens instead of account passwords.
9. Scan Docker images for vulnerabilities.
10. Use non-root containers where possible.
11. Regularly update the Node.js base image.
12. Remove unused Docker images and containers.

24. FINAL DEPLOYMENT FLOW
=========================

The final deployment process is:

1. Developer changes Konexa source code.
2. Code is committed to GitHub.
3. Jenkins retrieves the konexa-v3-docker branch.
4. Jenkins builds the Docker image.
5. Jenkins validates the image.
6. Jenkins logs into Docker Hub.
7. Jenkins pushes the versioned image.
8. Jenkins pushes the latest image.
9. Jenkins connects to EC2 through SSH.
10. EC2 pulls the latest Docker image.
11. Existing Konexa Docker container is removed.
12. New Konexa container starts.
13. Port 3000 is exposed.
14. Jenkins performs a health check.
15. Unused Docker images are cleaned.
16. Pipeline reports SUCCESS.
